06 · debugging notes

StreakTrack: the 403 that wasn't permitAll()

The bug

Deployed the Spring Boot backend to Render. POST /api/auth/register and POST /api/auth/login both returned HTTP 403 Forbidden — even though everything on paper looked correct:

  • Spring Boot 3.3.4, Spring Security configured
  • /api/auth/** set to permitAll()
  • CSRF disabled, CORS configured
  • Controller mapping and request DTO matched
  • Backend running fine on Render

Root cause

It wasn't the security config or the controller — it was the custom JWT filter. The filter ran on every request, including public auth endpoints, and rejected requests with no token before they ever reached the permitAll() rule. permitAll() only tells Spring Security's authorization layer to allow the route — it doesn't stop custom filters in the chain from running and rejecting the request first.

The fix

Updated the JWT filter to skip public auth routes (/api/auth/register, /api/auth/login) and let unauthenticated requests to those paths pass through untouched, instead of blocking them before the security chain even evaluated permitAll().

Resolved — both endpoints return 200
Lesson: permitAll() governs authorization, not the filter chain. Any custom filter still runs first and can reject a request before Spring Security's rules are even checked.

Ledger — Core Banking Engine: how it's built, and what I fixed along the way

How it works

Ledger models the account logic behind a real bank's ledger, built around a small, focused class hierarchy:

  • Account — abstract base class holding balance, owner, and transaction history
  • CheckingAccount / SavingsAccount — subclasses overriding available-funds rules (overdraft vs. interest)
  • Transaction — an immutable log entry with timestamp, type, amount, optional note, and optional counterparty
  • Bank — owns all accounts, opens new ones, and coordinates transfers between them
  • BankApp — console menu that wires it all together (deposit, withdraw, transfer, view history, apply interest)

The bug

Two separate issues showed up while building this. First, CheckingAccount's $100 overdraft support was implemented by duplicating balance-adjustment logic directly in the subclass, which got messy and error-prone fast. Second, Bank.transfer() called the normal withdraw()/deposit() methods and a separate logging call — which meant every transfer wrote two transaction entries per account instead of one.

Root cause

Account kept its balance field fully private with no shared hook for subclasses to safely adjust it, so CheckingAccount had no clean way to plug in overdraft rules other than re-implementing withdraw from scratch. Separately, withdraw()/deposit() already logged a transaction internally — so the extra manual logging call after them was redundant, and nothing caught the duplication because each call looked correct in isolation.

The fix

Refactored Account to expose two protected hooks: getAvailableFunds() (which CheckingAccount overrides to add the $100 overdraft) and applyBalanceChange() (a single method that adjusts the balance and logs exactly one transaction). Added dedicated transferOut()/transferIn() methods so each leg of a transfer logs once, with the counterparty's account number and name attached — instead of double-logging through generic withdraw/deposit calls.

Resolved — every transaction now logs exactly once, overdraft logic lives in one place
Lesson: when a subclass needs to bend a rule (like allowing overdraft), give it a single protected hook to override — not a reason to re-implement the whole method.

What's next

  • Persist accounts to a real database (PostgreSQL) instead of in-memory storage
  • Wrap the same logic in a Spring Boot REST API layer
  • Add JUnit tests covering transfers, overdraft limits, and interest calculations
  • Add concurrency safety for simultaneous transactions on the same account

MERA — Stock Agent Showdown: three silent failures between a finished build and a live link

The bug

The game was complete as a single index.html. Shipping it to GitHub Pages surfaced three failures, none of which raised an error message:

  • Repo setup: the file name index.html was entered in the repository name field
  • Upload: the file landed as index (1).html instead of index.html
  • Publish: Pages reported currently disabled and the live URL served nothing

Root cause

  • File name vs. repo name. The repo name becomes part of the URL path, so the site would have been served from username.github.io/index.html/.
  • Duplicate download. The browser auto-appended "(1)" to a second download of the same file. Pages resolves a site's default document by exact filename, and index (1).html doesn't match, so the root would have returned a 404.
  • Commit is not deploy. A push only stores files. Pages has no publish source until a branch and folder are selected and saved.

The fix

  • Created the repo as mera-stock-showdown, set to Public so the source is readable and the app is playable
  • Renamed the file to index.html in GitHub's editor and committed the change
  • Settings → Pages → Deploy from a branch → main → / (root) → Save
  • Confirmed the "pages build and deployment" workflow completed, then loaded the URL in a private window to rule out a cached 404
Resolved — live at merhawi7.github.io/mera-stock-showdown, source public
Lesson: static hosting fails silently, so validate the deployment before debugging the code. Check the entry filename, the publish source, then the cache, in that order.

Pre-deploy audit

Before publishing, I audited the file for anything that only works in its original environment: API calls, custom storage APIs, and external scripts. It had none. The only external request is Google Fonts, with a fallback stack, and best runs use localStorage, which works on GitHub Pages and stays private to each player's browser. The result is a zero-dependency single-file deploy.
